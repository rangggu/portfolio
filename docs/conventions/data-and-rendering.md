# Data & Rendering

## 렌더링 전략

기본은 정적 생성이고, 필요한 곳만 동적으로 전환합니다. `fetch()`는 기본적으로 캐시하지 않습니다(`no-store`). 캐시가 필요하면 `cache: 'force-cache'` 또는 `next: { revalidate: N }`을 명시합니다.

| 대상                                                                             | 방식                                                                               |
| -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 7개 프레임 라우트 (/, /about, /career, /projects, /skills, /education, /contact) | 완전 정적 생성. 같은 캔버스 레이아웃 공유, 초기 프레임만 다름                      |
| 케이스 스터디 (/projects/[slug])                                                 | 정적 생성 (`generateStaticParams`). 직접 접근 시 단독 페이지, 프레임에서 열면 모달 |
| 케이스 스터디, 소개 페이지                                                       | 완전 정적 생성                                                                     |
| 서버에서 가져오되 가끔 바뀌는 데이터                                             | fetch의 `next: { revalidate: N }`으로 주기적 갱신 (ISR)                            |
| 반응 수 등 자주 바뀌는 값                                                        | 페이지를 동적으로 만들지 않고, 클라이언트에서 fetch하여 표시                       |
| 요청마다 달라야 하는 데이터                                                      | 해당 영역만 동적 렌더링                                                            |
| 반응 버튼 등 사용자 액션                                                         | Server Actions                                                                     |
| AI 에이전트, 스트리밍 데모                                                       | Route Handler (`app/api/`)에서 스트리밍 응답                                       |

- 페이지를 동적으로 만드는 API(`cookies()`, `headers()`, 캐시하지 않는 fetch)는 필요한 컴포넌트 안에서만 씁니다.
- 동적 영역은 `<Suspense>`로 감싸 정적 부분이 먼저 보이게 합니다.
- 정적 생성을 유지하기 위해, 자주 바뀌는 데이터(반응 수, 조회 수 등)는 서버 컴포넌트에서 불러오지 않고 클라이언트 컴포넌트에서 마운트 후 fetch합니다. 서버에서 불러오면 페이지 전체가 동적 렌더링으로 바뀌기 때문입니다.

## 서버 데이터 연동

```
lib/api/{domain}/
  ├── {domain}Api.ts      # fetch 함수 (서버 전용, 'server-only')
  ├── {domain}Dto.ts      # 요청·응답 타입 (snake_case)
  └── {domain}Mapper.ts   # DTO → UI 모델 변환
```

- fetch 함수는 `get*`, `post*`로 이름 짓고, 반환 전에 mapper를 거칩니다.
- 도메인 기준은 엔드포인트 경로의 첫 번째 리소스입니다 (`/projects/...` → `project`).
- 빌드 타임에 불러오는 데이터는 서버 장애 시 빌드가 실패하지 않도록 폴백 데이터를 둡니다.

## Server Actions

- `features/{feature}/actions.ts`에 두고 파일 상단에 `'use server'`를 씁니다.
- 입력값은 서버에서 다시 검증합니다.
- 즉시 반영이 필요한 UI는 `useOptimistic`으로 먼저 반영하고, 실패하면 되돌린 뒤 토스트로 알립니다.
- 공개 액션(반응 버튼, AI 채팅)에는 rate limit을 겁니다.

## 상태 관리

| 유형                                     | 방식                                                                    |
| ---------------------------------------- | ----------------------------------------------------------------------- |
| 서버 데이터                              | 서버 컴포넌트에서 불러와 props로 전달                                   |
| 로컬 UI 상태                             | `useState`                                                              |
| 공유·재방문 가능한 상태 (필터, 탭)       | URL `searchParams`                                                      |
| 테마                                     | `<html data-theme>` + localStorage, 첫 페인트 전 인라인 스크립트로 적용 |
| 여러 컴포넌트가 공유하는 클라이언트 상태 | `useSyncExternalStore` 기반 소형 스토어 (`_state/`)                     |

- 전역 상태 관리 라이브러리는 도입하지 않습니다.
- 서버 데이터를 클라이언트 스토어에 복사해 두지 않습니다.
- 스토어는 기능별로 나누고, 구독할 때는 필요한 필드만 셀렉터로 고릅니다.

## 에러 처리

- 라우트 세그먼트마다 필요한 곳에 `error.tsx`, `not-found.tsx`를 둡니다.
- **데이터가 없으면 기능을 숨깁니다 (graceful degradation).** 예를 들어 반응 수를 못 불러오면 숫자만 숨기고 버튼은 유지합니다.
- 사용자에게 보이는 에러는 원인 대신 다음 행동(다시 시도 등)을 안내합니다.
- 에러를 조용히 삼키지 않습니다. `catch`에서 처리하지 않을 거면 로그를 남기고 다시 던집니다.
- 스트리밍 데모처럼 에러 자체가 기능인 곳은 에러 상태를 명시적인 UI 상태(`STREAM_STATUS.ERROR`)로 다룹니다.
